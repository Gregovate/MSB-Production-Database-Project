## Before You Begin

This lesson explains what happens after you have submitted a Pull Request for review.

Review comments are a normal part of working with shared documentation.

Receiving review comments does **not** mean you did something wrong.

The review process exists to help improve the documentation before it becomes part of the official MSB project.

---

# What Is a Review?

After you submit your Pull Request, another person reviews your work.

The reviewer will compare:

* The original document.
* Your proposed changes.

The reviewer checks for things such as:

* Accuracy
* Consistency
* Spelling and grammar
* Broken links
* Formatting
* Technical correctness
* Whether the changes fit the style of the existing documentation

---

# Possible Review Results

After reviewing your work, one of several things may happen.

## Approved

Everything looks good.

Your Pull Request is approved and can be merged into the official documentation.

Congratulations!

---

## Minor Suggestions

The reviewer may suggest small improvements.

For example:

* Correct a spelling mistake.
* Improve wording.
* Clarify a sentence.
* Adjust formatting.

These are common and should not be taken personally.

---

## Changes Requested

Sometimes a reviewer will request one or more corrections before approving the document.

This simply means the document needs a little more work before becoming part of the official project.

---

# Reading Review Comments

Review comments are usually attached directly to your Pull Request.

Read every comment carefully before making changes.

Take your time.

Many comments are suggestions intended to make the document clearer for future readers.

---

# Don't Rush

Before making changes:

Read all of the comments first.

Often several comments relate to the same topic.

Understanding the review as a whole usually produces a better result than fixing one comment at a time.

---

# Return to Visual Studio Code

Open your MSB project in Visual Studio Code.

Locate the document mentioned in the review comments.

Open the document.

---

# Make the Requested Changes

Edit the document just as you did before.

When making corrections:

* Keep the existing document style.
* Verify your formatting.
* Save your work.
* Preview the document.

Take the same care you used when creating the original document.

---

# Save the Document

Press:

```text
Ctrl + S
```

or choose:

**File → Save**

Remember:

Saving updates **your copy** of the project.

It does not immediately update the official documentation.

---

# Review the Changes Again

Open **Source Control**.

Review the changes exactly as you did previously.

Confirm that only the intended corrections were made.

---

# Commit the Corrections

Write another short commit message describing the changes.

Examples:

```text
Address review comments

Correct formatting requested during review

Clarify installation procedure

Update screenshots after review
```

Commit the changes.

---

# Publish the Updated Changes

After committing:

Publish or Push your changes.

GitHub automatically adds the new changes to the existing Pull Request.

**Do not create a second Pull Request for the same work.**

The original Pull Request remains open until the reviewer approves it.

---

# Tell the Reviewer What You Changed

After updating your Pull Request, it is helpful to leave a short reply.

Examples:

> Updated the installation steps as requested.

or

> Corrected the screenshots and fixed the broken links.

or

> I addressed each review comment. Please let me know if you would like any additional changes.

A short message lets the reviewer know that your work is ready for another review.

---

# If You Don't Understand a Comment

Sometimes a review comment may not be completely clear.

That is normal.

Do **not** guess.

Instead:

Reply to the comment and politely ask for clarification.

For example:

> I want to make sure I understand your suggestion correctly. Could you explain what you would like changed in this section?

It is much better to ask than to make the wrong change.

---

# If You Disagree With a Comment

Occasionally you may believe your original wording is correct.

That is acceptable.

Instead of ignoring the comment:

Reply politely and explain your reasoning.

Good documentation is often improved through discussion.

The goal is to produce the best document, not to "win" an argument.

---

# Avoid These Common Mistakes

## Creating a New Pull Request

Do **not** create another Pull Request for review corrections.

Continue working in the original Pull Request.

---

## Ignoring Comments

Read every review comment.

If you intentionally decide not to make a suggested change, explain why.

---

## Making Unrelated Changes

While correcting review comments, avoid making additional unrelated improvements.

Keep the Pull Request focused on the original topic.

If you discover another issue, consider submitting it later as a separate Pull Request.

---

## Deleting Reviewer Comments

Review comments become part of the discussion history.

Leave them in place.

Instead, respond to the comments after making your corrections.

---

# When the Pull Request Is Approved

After the reviewer is satisfied:

The Pull Request will be approved.

The approved changes will be merged into the official MSB documentation.

At that point:

* Your work becomes part of the project.
* Other contributors will receive the updated documentation during their next update.
* Your Pull Request is complete.

Congratulations!

---

# Learning From Reviews

Every review helps improve both the documentation and your editing skills.

Over time you will begin to recognize common suggestions such as:

* Improving clarity.
* Using consistent terminology.
* Keeping procedures organized.
* Writing shorter, easier-to-follow instructions.

Most experienced contributors receive review comments from time to time.

That is simply part of maintaining high-quality documentation.

---

# What You Have Learned

You now know how to:

* Read review comments.
* Update your documents.
* Commit additional corrections.
* Update an existing Pull Request.
* Communicate with the reviewer.
* Complete the review process.

At this point you have learned the complete workflow used to contribute documentation to the MSB project.
