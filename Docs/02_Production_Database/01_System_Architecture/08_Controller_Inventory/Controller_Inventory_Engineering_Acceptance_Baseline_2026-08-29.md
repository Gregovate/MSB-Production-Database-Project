## Purpose

This document is the durable current Controller Inventory engineering checkpoint.

It exists specifically so accepted architecture, grouping rules, current evidence, corrected assumptions, unresolved questions, and the exact resume point do not depend on ChatGPT conversation history or a temporary spreadsheet.

The working spreadsheet is temporary engineering evidence. It is not the future Controller Inventory system and it is not an operational source of truth.

## Authority Chain

The accepted authority boundary is:

```text
Light-O-Rama / current approved V7 materialization
    -> authoritative current show wiring and addressing

Controller Inventory engineering reconstruction
    -> best current physical-controller grouping interpretation
       built from LOR wiring + controller-family behavior + known field facts

Future PostgreSQL Controller Inventory
    -> permanent physical controller identity
       accepted current physical relationships/groupings
       model/firmware/status facts owned by Production Database

FieldWiring
    -> technician-facing consumer of current LOR wiring
       enriched by Controller Inventory physical-controller facts
```

LOR owns current wiring facts such as Network, UID, channel/output, universe, Preview/Scene/Display relationships, and SPARE state.

Controller Inventory must not create an editable competing copy of those LOR facts merely to make physical-controller grouping easier.

## Permanent Controller Identity — Accepted

There is one permanent physical controller identity:

```text
ref.controller.controller_id
```

`controller_id` will be generated by PostgreSQL and follows the same identity principle as `ref.display.display_id`.

The accepted scan payload is:

```text
CTRL:<controller_id>
```

Do not create any second permanent key such as:

```text
controller_key
CL-###
CTRL:CL-###
```

Network, UID/range, IP address, universe, Display, Stage, Scene, COM port, workbook row, and LOR Prop identity are configuration/context evidence, not permanent physical identity.

## Current Controller-to-Display Relationship — Accepted

The current physical relationship is many-to-many:

```text
one controller -> zero, one, or many Displays
one Display    -> zero, one, or many controllers
```

A future relationship such as `(controller_id, display_id)` must therefore permit both directions. Do not impose `UNIQUE(display_id)`.

This relationship means only that a physical controller currently serves a physical Display. It does not copy Network, UID, channel, universe, Stage, or IP into a competing Controller Inventory topology.

## Address Reuse — Accepted

LOR addressing identifies programmed show behavior, not permanent physical hardware identity.

The same Network + UID/range + channel may legitimately apply to more than one physical controller.

Confirmed patterns include:

- HWY-42 traffic-sign controllers intentionally sharing `Regular / UID 09 / channel 1`;
- Church repeated Pixie4 Candy Cane blocks;
- Candyland repeated Pixie4 Candy Cane blocks; and
- other physical copies that use the same programmed address in separate physical contexts.

Never enforce physical-controller uniqueness on Network + UID/range or Network + UID + channel.

## Controller-Family Grouping — Accepted

The grouping method is family-specific.

### Conventional LOR A/C

Current `Network + UID` defines an addressed LOR controller/command context. `start_channel` is the physical numbered output for conventional A/C hardware.

All current Display relationships under that addressed context can be grouped electrically from LOR. That electrical context does not by itself prove there is exactly one physical box when identical addressing is intentionally reused.

### Pixie

Pixies span model-specific UID blocks. A physical Pixie2/Pixie4/Pixie8/Pixie16 may occupy multiple UIDs while remaining one physical controller.

Unused positions in a physical UID block are valid and must not make the controller grouping fail merely because not every possible UID currently appears in LOR.

### E1.31 / dense RGB

Universe and IP address are configuration, not permanent controller identity.

Physical-controller/output grouping must use the current LOR/E1.31 wiring evidence plus reviewed physical controller/output semantics. Controller Inventory should provide enough accepted physical mapping for FieldWiring to resolve the physical controller/output without duplicating every LOR universe/channel row.

### DMX / fixtures

A DMX fixture relationship is not automatically a Controller Inventory controller asset. For example, the CR50 fixture grouping used by FieldWiring remains a LOR/FieldWiring wiring-presentation concern unless the physical gateway or managed controller serving it is separately in Controller Inventory scope.

## Working Spreadsheet — Exact Role

The current `Controller Inventory & Testing 2026(...)` workbook is a **temporary engineering grouping worksheet**.

It is not:

- current wiring authority;
- permanent controller identity authority;
- an authoritative physical inventory already known to be complete;
- a future operational workflow; or
- a database that PostgreSQL must mirror row-for-row.

The workbook is an attempt to assemble the best physical-controller groupings possible before the complete physical inventory is presented/verified.

The current working `Controller Inventory & Testing 2026(7).xlsx` list contains **deployed/assigned controllers only**. It contains no known spare/available controller rows. Therefore a workbook row whose permanent Display relationship is not yet resolved remains a deployed-controller review item and must not be reclassified as available stock merely because assignment resolution is incomplete.

Available/unassigned controller inventory begins outside this workbook and will be created only when actual spare/unassigned physical hardware is discovered or deliberately added through the future Controller Inventory workflow.

Controller-to-Display assignment is independent of current physical storage/deployment location. An assigned controller may remain assigned while physically stored in the workshop/warehouse between setup seasons.

The groupings are educated engineering reconstructions based on how the authoritative LOR wiring comes together, controller-family behavior, known physical facts, model/capability information, location clues, and operator knowledge.

### `For What` column

The final workbook column, `For What`, was deliberately added to define or distinguish the **proposed physical grouping/use context** when the other columns are insufficient.

It must not be treated as incidental comments.

Examples of information this field may carry include:

- a physical subgroup such as `Candy Canes 1-4` versus `Candy Canes 5-8`;
- North/South or similar repeated-address physical distinctions;
- the physical purpose of an otherwise ambiguous controller; or
- a current grouping clue needed to explain how several LOR relationships are believed to map to one or more physical boxes.

The future PostgreSQL design should not blindly copy the free-text column. Instead, repeated information that proves structurally necessary during this fit test is evidence for the relationship/context the final schema must represent.

## Grouping Acceptance Process

The Pre-DDL process is now explicitly an acceptance workflow rather than an informal spreadsheet cleanup exercise.

For each proposed physical grouping:

1. Start with current LOR/V7 wiring as the authoritative electrical/topology evidence.
2. Apply the applicable controller-family semantics.
3. Use the workbook grouping, `For What`, model/capability evidence, location evidence, and known field facts as the best current physical reconstruction.
4. Check whether the grouping can explain the LOR wiring without violating known controller capability or known physical facts.
5. Do not reject a grouping merely because LOR cannot independently prove the number of physical boxes. LOR often cannot distinguish identically programmed physical controllers.
6. Record material accepted groupings, corrected assumptions, unresolved ambiguity, and the current resume point in controlled Controller Inventory engineering documentation as the work proceeds.
7. Do not let a grouping become durable project knowledge only in chat or only in the spreadsheet.

### Acceptance states

Use these engineering states conceptually during the Pre-DDL review:

```text
PROPOSED
    best current grouping hypothesis; still under review

ENGINEERING_ACCEPTED
    grouping fits current LOR wiring, controller-family behavior,
    and all presently known physical facts well enough to use for
    schema/relationship design and bootstrap planning

FIELD_VERIFICATION_REQUIRED
    grouping cannot yet be distinguished or confirmed sufficiently;
    preserve the ambiguity rather than guessing

PHYSICALLY_VERIFIED
    later field/inventory inspection has confirmed the actual hardware

SUPERSEDED
    an older grouping or source assumption was replaced by better evidence
```

`ENGINEERING_ACCEPTED` does **not** claim that the complete physical inventory has already been inspected. It records the best accepted engineering grouping based on the evidence currently available.

## No Spreadsheet in the Future System

The spreadsheet is a bootstrap/reconstruction tool only.

Once the Controller Inventory subsystem is implemented and accepted:

```text
PostgreSQL Controller Inventory
    = permanent controller/device identity and accepted Production Database-owned physical relationships

Controller Inventory application/workflow
    = controlled maintenance of those physical facts

LOR/V7
    = current wiring/addressing authority

spreadsheet
    = historical bootstrap evidence only; not an ongoing operational dependency
```

Do not design a future periodic spreadsheet-import process as the normal Controller Inventory workflow.

## FieldWiring Consumer Contract

The current FieldWiring handoff remains a required consumer contract.

FieldWiring needs Controller Inventory eventually to provide enough accepted physical information to answer:

- which permanent controller applies to a current LOR wiring context;
- exact model/family and physical capability;
- the physical output/port or reviewed basis used to derive it where applicable;
- the distinguishing physical group when identical addressing is intentionally reused; and
- current assignment/reconciliation provenance relative to the approved LOR/V7 state.

FieldWiring continues to obtain detailed current wiring rows from LOR/V7. Controller Inventory supplies the physical-controller facts that LOR cannot encode.

## Managed Hardware Scope

Permanent Controller Inventory identity may apply to managed show-control devices beyond light-output controllers, including Directors, Easy Light Linkers, InputPup, PixieLink, ServoDog, and other controlled hardware.

A managed device does not require a Display assignment merely because it has a permanent `controller_id` or firmware.

## History Boundaries

Controller deployment/Display/address assignment history is not required for V1. Current physical assignment is sufficient.

Firmware history is retained by permanent `controller_id`.

Repairs and maintenance belong in Work Orders linked to `controller_id` rather than a duplicate Controller Inventory repair-history subsystem.

## DDL Gate

Do not create final production-authoritative Controller Inventory PostgreSQL tables or migrations until the current grouping/application fit test establishes that the proposed physical identity/relationship model can represent the actual system without forcing LOR addressing to become permanent identity or forcing unsupported physical guesses into permanent data.

Before final DDL acceptance, engineering must have a durable record of:

- accepted identity and many-to-many relationship rules;
- family-specific grouping behavior;
- repeated-address handling;
- how unresolved physical ambiguity is represented;
- model/firmware authority requirements;
- technician write boundaries;
- audit/actor requirements under Production Database standards; and
- the accepted Controller Inventory read contract required by FieldWiring.
