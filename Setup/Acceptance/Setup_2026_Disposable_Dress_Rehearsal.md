# 2026 Setup Disposable Dress Rehearsal

## Purpose

This is the pre-Production team rehearsal for the 2026 Setup operating spine.

It is intentionally broader than a single feature review. The team should use the real Setup browser workflow against a disposable current-Production clone, decide how the task lists should work in practice, and change the candidate design before the real 2026 Production Session is used for field work.

Production is not writable during this rehearsal.

## Starting State

The rehearsal preparation SQL:

`Setup/Acceptance/setup_122_2026_dress_rehearsal_seed.sql`

creates only:

- a disposable 2026 Setup Session;
- the annual task snapshot generated by the current reusable Setup Catalog.

It deliberately creates **no**:

- work days;
- crews;
- scheduled assignments;
- progress/work-report rows;
- movement events;
- Work Order Intake records.

The schedule must be built in the browser because schedule creation and downstream list behavior are what the team is reviewing.

## Personas

Use two browser identities against the same disposable PostgreSQL clone.

### Manager browser

The Manager should be able to:

- create Setup work days;
- create/adjust crews;
- assign Captains;
- assign/reassign/reorder annual tasks;
- review the generated Captain Work List;
- review the generated Pick List;
- review Work Order Intake after a field finding is submitted.

### Production Crew browser

The Production Crew user should be able to:

- read current scheduled work;
- open the Captain Work List;
- open the Pick List;
- open task Procedure/material context;
- Report Work with actual crew + elapsed Hours/Minutes + progress;
- explicitly mark work complete when the completion point is actually reached;
- Report Problem / Suggest Change into Work Order Intake.

The Production Crew user must **not** be able to mutate the schedule or reusable Catalog.

## Rehearsal Sequence

### 1. Build a realistic near-term schedule

From the Manager browser:

1. select 2026;
2. create one or more work days;
3. add the number of crews expected for those days;
4. assign a Captain where useful;
5. schedule representative annual tasks;
6. use real shifts/crew assignments rather than arranging rows only for appearance.

Include enough variety to exercise:

- more than one Stage/Scene;
- more than one crew;
- a task with prerequisites;
- a task with readiness/weather guidance;
- a task with Displays/Containers;
- a task with Kit/support material;
- Extra Material where available;
- a Procedure-backed task.

### 2. Review the Captain Work List

Open **Captain Work List**.

The team should decide whether the current presentation is useful in the field:

- grouping by day / crew / shift;
- task order;
- Stage/Scene visibility;
- Can start when;
- Weather limits;
- Done when;
- Important setup notes;
- expected/planned crew;
- expected duration;
- prerequisites;
- Equipment / Resources;
- material summary;
- Procedure;
- Report Work;
- Report Problem / Suggest Change.

Change the schedule in the Manager browser and confirm the list changes accordingly.

Review both phone-width and print presentation.

The first layout is not considered final merely because it renders correctly.

### 3. Review the Pick List

Open **Pick List**.

Confirm that scheduled work resolves to physical demand and that shared physical items are deduplicated while preserving every reason they are needed.

Review:

- Container / detached Display identity;
- home/storage information;
- staged-by / needed-for timing;
- all scheduled reasons;
- unresolved material-authority warnings.

Change the schedule and confirm the Pick List changes without creating movement history.

### 4. Report actual work

From the Production Crew browser, open **Report Work** from the scheduled task.

Confirm the scheduled context is inherited automatically.

Enter:

- actual crew size;
- Hours;
- Minutes;
- optional quantity/units;
- progress/completion note;
- Task Complete only when appropriate.

Verify the progress history preserves each work period rather than collapsing multi-day work into one fabricated duration.

### 5. Report a field problem/change

From the same task context choose **Report Problem / Suggest Change**.

The reporter should enter only:

- what they found;
- optional suggested change.

Setup should automatically preserve the known season/task/Stage/Scene/day/shift/crew/reporter context.

Confirm the submission creates a **Work Order Intake** record only.

It must not create an active Work Order until a Manager promotes it through triage.

### 6. Replan from actual evidence

Return to the Manager browser.

Use the reported progress/completion state to adjust the next work day.

The goal is to prove the loop:

```text
plan
-> Captain/Pick Lists
-> perform
-> Report Work
-> field finding -> Intake/Triage
-> replan
```

## Team Design Questions

The rehearsal is expected to produce design changes. Capture decisions about:

- how the Captain list should be grouped;
- whether the default should be one Captain/crew or all crews;
- information order and density;
- what belongs on phone vs print;
- whether Procedure should remain link-only or expose more preview context;
- Pick List grouping and material verbosity;
- wording that is unclear to the crew;
- anything the team has to re-enter even though Setup already knows it.

Do not modify durable Production data merely to make the rehearsal look realistic. Change the disposable schedule and candidates instead.

## Safety Boundary

The reusable browser runner:

- captures Production with `pg_dump` and read-only evidence;
- restores a disposable clone;
- applies candidate migrations only to the clone;
- runs Manager and optional Production Crew preview processes against that same clone;
- cleans the clone and preview processes at the end;
- verifies the Production Setup fingerprint and live Setup checkout SHA are unchanged.

A successful rehearsal is not Production deployment authorization.
